# Channel playbooks

Two channels. Warm referrals convert trust that already exists; the marketplace supplies buyers who have already said what they need. Both run under the same caps and the same human send gate.

## Warm referrals

**Who:** former colleagues, managers, clients of a previous employer the operator personally worked with, technical peers, friends who run or work in small businesses. Not purchased lists, not scraped contacts.

**The ask is for an introduction, not a sale.** The connector is not the buyer. Never score the buyer on the connector's enthusiasm; the buyer stays HOLD until spoken to directly.

Shape of the ask:

> I've gone independent doing [one concrete kind of work, e.g. connecting systems that don't talk to each other and automating the manual steps between them]. Who do you know still doing [the manual version, e.g. re-keying orders between two systems every morning] by hand?

Why it works: it names a recognizable problem, so the connector can pattern-match a real person; it asks for a name, not a favor; it does not ask them to vouch for unproven results.

Rules for the warm ask:

- Never request private lists, contact exports or a forwarded email thread.
- Never imply the connector endorses the work.
- One ask per person per round; a non-answer is a non-answer.
- After an introduction, qualify the actual buyer with the rubric before proposing anything.
- After any delivery, make two asks: the next piece of work, and who else has the same problem.

## Freelance marketplace (Upwork)

**What to look for:** a posting that describes one concrete broken flow, manual burden or desired outcome in a stack the operator can deliver.

**Screen in this order:**

1. Hard stops from the rubric (ineligible, staffing seat, unfunded, unsafe, fabrication required).
2. Client payment history and terms. Verified payment and prior hires raise funding confidence; "pay only if it works" is a hard stop.
3. Scope: can it be bounded to one flow, one document type or one environment?
4. Proof requirements. "Two production examples of this exact project" is a trust barrier for a zero-review profile; bid only if self-built proof genuinely matches, never invent it.
5. Posting age and proposal count are preferences, not filters. They never substitute for fit.

Check current platform fees and bid-credit costs at proposal time; they change, and they count against the acquisition spend cap.

**Proposal structure (in this order):**

1. Their problem in their words, plus one detail that proves the post was read.
2. The bounded approach: what gets checked first (native settings, existing connector), what gets built only if needed, what "done" means.
3. Relevant self-built proof, named plainly. No client claims that do not exist.
4. Price basis: fixed price for a bounded scope, or a paid diagnostic first when root cause is unknown.
5. One next step.
6. One plain sentence that the preference is an ongoing working relationship, not a one-off. Once. Not presumptuous, not repeated.

Lead with the outcome and the approach. Skip front-loaded disclaimers about what the operator has not done; state willingness to learn only where it is true and relevant.

## Follow-up

- At most one follow-up per recipient, after five business days, separately approved.
- Silence never expands permission. No third touch, no channel-hopping to reach the same person.

## Approval packet

Volume channels batch review into one packet per channel per day (e.g. "5 proposals, final text attached"). Approval is still per recipient. Each item lists:

| Field | Why |
|---|---|
| Destination and recipient | Prevents the wrong person or the wrong thread |
| Final message and attachments | Approval covers exactly this text; any edit needs fresh approval |
| Timing | Sends happen when approved, not whenever |
| Cost | Bid credits or fees counted against the spend cap |
| Score and evidence | The reviewer can reject a weak lead, not just a weak sentence |

The human sends. The agent records "sent" only after confirming the message went out.
